## 1. 整体架构

### 1.1 高层次流程

X 的 "For You" 推荐系统采用**模块化、可组合的管道架构**：

```
用户请求 → Home Mixer → 查询扩充 → 候选源获取 → 内容扩充 → 过滤 → 评分 → 选择 → 后处理 → 响应
```

### 1.2 核心组件

#### A. Home Mixer（编排层）
- 中央编排器，组装整个推荐管道
- 暴露 gRPC 端点（`ScoredPostsService`）用于获取排序后的帖子
- 实现 `CandidatePipeline` 框架进行结构化执行
- 全程提供可配置的错误处理、日志记录和监控

#### B. Thunder（网络内帖子服务）
- 实时、内存中的帖子存储，用于最近创建的帖子
- 消费 Kafka 事件进行帖子创建/删除
- 为每个用户维护以下存储：
  - 原创帖子（非回复、非转发）
  - 次级帖子（回复和转发）
  - 视频帖子
- 实现**亚毫秒级**查找 "网络内" 内容（来自关注账户的帖子）
- 默认保留时间：**2天**；可在运行时调整

#### C. Phoenix（基于ML的检索与排名）
- **检索阶段**：双塔模型用于网络外发现
  - 用户塔：编码用户特征 + 互动历史 → 用户嵌入向量
  - 候选塔：编码所有帖子 → 候选嵌入向量
  - 相似度搜索：点积相似度获取 Top-K
- **排名阶段**：带候选隔离的 Transformer
  - 预测 **15+ 种互动类型**的概率
  - 特殊注意力掩码防止候选之间相互关注
  - 每个帖子仅基于用户上下文独立评分

#### D. 候选管道框架
- 可复用的基于特征的架构，包含可组合阶段：
  - QueryHydrator, Source, Hydrator, Filter, Scorer, Selector, SideEffect
- 尽可能并行执行以提高效率
- 带请求 ID 追踪的优雅错误处理

## 2. 推荐流程管道

### 2.1 阶段一：查询扩充

**输入**：用户ID、客户端信息、已看/已服务的帖子ID、布隆过滤器

**扩充器**：

1. **UserActionSeqQueryHydrator**
   - 获取用户的互动历史（点赞、回复、分享等内容）
   - 供 Phoenix 模型用作个性化上下文

2. **UserFeaturesQueryHydrator**
   - 获取用户的社交图谱特征：
     - 关注的用户ID列表
     - 屏蔽的用户ID列表
     - 静音的用户ID列表
     - 订阅的用户ID列表
     - 静音的关键词列表

### 2.2 阶段二：候选源获取

**两个并行源合并在一起**：

| 来源 | 描述 | 数量限制 | 标记 |
|------|------|----------|------|
| **Thunder（网络内）** | 从用户关注的账户获取最近帖子 | 约500条 | `ForYouInNetwork` |
| **Phoenix（网络外）** | 使用检索模型从整个语料库中找到相似帖子 | 约1000条 | `ForYouPhoenixRetrieval` |

### 2.3 阶段三：候选扩充

用额外元数据丰富候选内容：

1. **InNetworkCandidateHydrator** - 标记帖子为网络内
2. **CoreDataCandidateHydrator** - 获取核心帖子数据（文本、媒体等）
3. **VideoDurationCandidateHydrator** - 获取视频时长元数据
4. **SubscriptionHydrator** - 识别付费墙内容
5. **GizmoduckCandidateHydrator** - 获取作者信息（用户名、粉丝数等）

### 2.4 阶段四：评分前过滤

**过滤链（顺序重要）**：

| 序号 | 过滤器 | 功能 |
|------|--------|------|
| 1 | **DropDuplicatesFilter** | 使用 HashSet 移除重复帖子ID |
| 2 | **CoreDataHydrationFilter** | 移除未能扩充核心元数据的帖子 |
| 3 | **AgeFilter** | 移除超过配置阈值的旧帖子（如30天） |
| 4 | **SelfTweetFilter** | 从用户自己的信息流中移除自己的帖子 |
| 5 | **RetweetDeduplicationFilter** | 去重转发：保留推文的首次出现 |
| 6 | **IneligibleSubscriptionFilter** | 移除用户未订阅的付费墙内容 |
| 7 | **PreviouslySeenPostsFilter** | 使用布隆过滤器 + seen_ids 列表移除已看帖子 |
| 8 | **PreviouslyServedPostsFilter** | 移除本次会话中已服务的帖子（避免重复） |
| 9 | **MutedKeywordFilter** | 使用分词器匹配并移除包含静音词的帖子 |
| 10 | **AuthorSocialgraphFilter** | 移除来自已屏蔽/静音作者的帖子 |

### 2.5 阶段五：多轮评分

#### 评分器 1：PhoenixScorer
- 调用 Phoenix 排名模型，传入用户上下文 + 候选
- 为每个候选提取 **18种互动概率**
- 存储在 `PhoenixScores` 结构中
- 附加预测请求ID和时间戳

#### 评分器 2：WeightedScorer
- 将18种概率分数与配置的权重组合
- 应用条件逻辑（如仅当视频时长 > 阈值时才应用VQV权重）
- 应用分数归一化和偏移以保持稳定性

#### 评分器 3：AuthorDiversityScorer
- 按加权分数（降序）排序候选
- 跟踪作者出现次数
- 根据作者位置乘以衰减函数
- **防止单一作者霸占信息流**

#### 评分器 4：OONScorer（网络外调整）
- 向下调整网络外分数
- 乘以 `OON_WEIGHT_FACTOR`（< 1.0）
- **确保网络内内容获得优先级**

### 2.6 阶段六：选择

**TopKScoreSelector**：
- 按最终分数（降序）排序所有候选
- 选择前 K 个候选（可配置，通常50-100个）

### 2.7 阶段七：选择后处理

**选择后扩充器**：
1. **VFCandidateHydrator** - 获取可见性过滤标签

**选择后过滤器**：
1. **VFFilter** - 根据可见性过滤服务移除已删除/垃圾/暴力/血腥内容
2. **DedupConversationFilter** - 去重同一对话线程的多个分支

### 2.8 阶段八：副作用

**CacheRequestInfoSideEffect**：
- 异步操作（不阻塞响应）
- 缓存请求信息供未来使用

## 3. 排名信号与权重

### 3.1 Phoenix Transformer 预测的18种互动类型

#### 正面互动（正权重）

| 信号 | 描述 | 重要性 |
|------|------|--------|
| `favorite_score` | 点赞概率 | ⭐⭐⭐⭐⭐ |
| `reply_score` | 回复概率 | ⭐⭐⭐⭐⭐ |
| `retweet_score` | 转发概率 | ⭐⭐⭐⭐⭐ |
| `quote_score` | 引用推文概率 | ⭐⭐⭐⭐ |
| `click_score` | 通用帖子点击 | ⭐⭐⭐ |
| `profile_click_score` | 访问个人资料 | ⭐⭐⭐ |
| `photo_expand_score` | 照片展开 | ⭐⭐⭐ |
| `video_view_score` | 视频观看完成度（VQV - 视频质量观看） | ⭐⭐⭐⭐ |
| `share_score` | 直接分享 | ⭐⭐⭐⭐ |
| `share_via_dm_score` | 通过私信分享 | ⭐⭐⭐⭐ |
| `share_via_copy_link_score` | 复制链接分享 | ⭐⭐⭐ |
| `dwell_score` | 停留时间 | ⭐⭐⭐ |
| `dwell_time` | 连续停留时长 | ⭐⭐⭐ |
| `follow_author_score` | 关注作者 | ⭐⭐⭐⭐ |

#### 负面互动（负权重）

| 信号 | 描述 | 惩罚程度 |
|------|------|----------|
| `not_interested_score` | 用户明确表示不感兴趣 | 🔻🔻🔻 |
| `block_author_score` | 屏蔽作者操作 | 🔻🔻🔻🔻🔻 |
| `mute_author_score` | 静音作者操作 | 🔻🔻🔻🔻 |
| `report_score` | 举报内容操作 | 🔻🔻🔻🔻🔻 |

### 3.2 最终分数计算

#### 加权评分公式

```
最终分数 = Σ (权重_i × P(互动_i))
```

其中：
- 正面互动具有正权重（点赞、回复、转发等）
- 负面互动具有负权重以进行惩罚
- 视频特定权重在视频时长超过最小阈值时条件性应用
- 加权组合后应用分数归一化
- 应用分数偏移以保持稳定性

#### 作者多样性调整

```
调整后分数 = 加权分数 × 乘数(位置)
其中 乘数(位置) = (1 - 下限) × 衰减因子^位置 + 下限
```

- 默认衰减因子：指数衰减（如0.8）
- 默认下限：最小保留分数阈值
- **防止信息流被单一作者主导**

#### 网络外调整

- 网络外（Phoenix发现的）帖子乘以 `OON_WEIGHT_FACTOR`
- **优先显示网络内内容**，同时仍包含多样化推荐

## 4. 内容过滤规则

### 4.1 评分前移除条件

| 过滤器 | 移除条件 |
|--------|----------|
| 年龄 | 创建时间超过30天（可配置） |
| 自己的帖子 | 由浏览用户发布 |
| 重复 | 精确帖子ID匹配 |
| 转发去重 | 相同底层推文已在结果中 |
| 已看 | 布隆过滤器匹配或在 seen_ids 列表中 |
| 已服务 | 当前会话中已服务 |
| 静音关键词 | 帖子文本包含静音关键词 |
| 已屏蔽/静音作者 | 帖子作者被屏蔽或静音 |
| 扩充失败 | 缺少核心元数据 |
| 不合格订阅 | 付费墙内容 + 用户未订阅 |

### 4.2 选择后移除条件

| 过滤器 | 移除条件 |
|--------|----------|
| 可见性过滤 | 已删除、垃圾信息、暴力、血腥、敏感内容 |
| 对话去重 | 同一线程的多个分支 |

## 5. 用户建模与个性化

### 5.1 用户上下文特征

#### UserActionSequence（来自互动历史）
- 用户最近点赞的帖子
- 用户最近回复的帖子
- 用户最近分享的帖子
- 用户最近举报/屏蔽的帖子
- 每个操作的时间戳

#### UserFeatures（社交图谱）
- 关注的用户ID（网络内范围）
- 屏蔽的用户ID
- 静音的用户ID
- 订阅的用户ID
- 静音的关键词

### 5.2 基于 Transformer 的个性化

Phoenix Transformer 接收以下输入：

1. **用户嵌入** - 使用多个哈希函数的用户哈希表示
2. **历史嵌入** - 用户最近操作的序列（帖子 + 作者 + 操作类型 + 产品界面）
3. **候选嵌入** - 每个候选的帖子 + 作者哈希

### 5.3 关键设计：候选隔离

```
┌─────────────────────────────────────────────────────────┐
│                    注意力掩码设计                        │
├─────────────────────────────────────────────────────────┤
│ 用户 + 历史位置：因果自注意力（可以相互关注）            │
│ 候选位置：可以关注用户/历史 + 只能关注自己               │
│ 候选之间：不能相互关注                                   │
└─────────────────────────────────────────────────────────┘
```

**优势**：
- 每个帖子获得独立分数，仅基于用户上下文
- 分数**不受**批次中其他帖子影响
- 启用缓存分数和一致结果

### 5.4 无手工特征工程

- 系统消除手动特征工程
- Transformer 从互动历史中学习所有信号
- **大幅降低数据管道复杂性**

## 8. 核心设计理念

### 8.1 候选隔离注意力掩码

特殊的 Transformer 掩码确保：
- 位置 0 到 candidate_start：因果自注意力（用户 + 历史）
- 候选位置：可以关注所有用户/历史 + 仅自己
- **启用独立评分和可缓存性**

### 8.2 无手工特征工程

- 所有信号从互动序列中学习
- **极大简化特征工程管道**
- Transformer 自动学习复杂交互

### 8.3 多动作预测

不是单一相关性分数：
- 预测 **18种不同的互动概率**
- 与可学习权重组合得到最终分数
- 捕捉细微差别：有些用户通过点赞互动，其他人通过回复

### 8.4 可组合管道架构

- 关注点分离：管道执行 vs 业务逻辑
- 易于添加新的源、过滤器、评分器、扩充器
- 尽可能并行执行以提高性能
- 一致的错误处理和日志记录

### 8.5 两阶段检索 + 排名

```
┌─────────────────────────────────────────────────────────┐
│        检索阶段                排名阶段                  │
├─────────────────────────────────────────────────────────┤
│  • 双塔模型                   • Transformer 模型        │
│  • 处理数十亿帖子              • 仅处理数百候选          │
│  • 高效 ANN 搜索              • 深度个性化评分          │
│  • 亚秒级延迟                 • 精确互动预测            │
└─────────────────────────────────────────────────────────┘
```

**大幅降低计算需求**

### 8.6 内存 Thunder 存储

- 网络内内容的**亚毫秒级**查找
- 避免数据库查询延迟
- Kafka 驱动的实时摄取
- 自动保留/修剪

## 9. 排名因素汇总表

| 信号类别 | 具体信号 | 权重类型 | 影响 |
|----------|----------|----------|------|
| **直接互动** | 点赞、回复、转发、引用 | 正权重 | 主要排名因素 |
| **内容交互** | 点击、个人资料点击、照片展开、视频观看 | 正权重 | 次要互动信号 |
| **分享** | 直接分享、私信分享、复制链接 | 正权重 | 高价值互动 |
| **停留时间** | 停留、停留时长 | 正权重 | 互动深度 |
| **关注意图** | 关注作者 | 正权重 | 关系建立 |
| **负面信号** | 不感兴趣、屏蔽、静音、举报 | 负权重 | 降低排名 |
| **多样性** | 作者重复衰减 | 乘数 | 分散在多个作者 |
| **来源类型** | 网络外调整 | 乘数 | 优先网络内 |
| **内容类型** | 视频时长条件 | 条件权重 | 视频特定提升 |

## 10. 性能优化

X 推荐系统采用的性能优化策略：

| 优化策略 | 描述 |
|----------|------|
| **并行执行** | 独立管道阶段并行处理 |
| **Async/Await** | 全程非阻塞 I/O |
| **布隆过滤器** | 高效的已看帖子过滤 |
| **基于哈希的嵌入** | 快速查找 |
